# 0.4 统一调度与三智能体

2026-11-08，用户明确授权本轮架构改造。新任务默认使用；不增加模型供应商、远程调用授权、生成范围或运行权限。

## 角色与闭环

| 角色 | 独立职责 | 可用权限 |
|---|---|---|
| 产品规划 planner | 冻结规格拆解、依赖任务、验收序号关联 | 受控源码/资料/已冻结知识证据读取，无修改或远程研究权限 |
| 开发 developer | 按任务实施、测试代码、依据审查意见修复 | 原有受控文件工具，唯一可修改源码的角色；仅任务明确启用才可公开研究 |
| 审查测试 reviewer | 独立读取当前源码与测试、逐条标记证据/缺口/待人工 | 只读工具和固定构建/测试，不能改源码、验收条件、预算或人工结论 |

调度是LangGraph代码，不新增第四个模型智能体。流程：用户确认 → 固定运行环境与工作区准备 → 规划智能体 → 开发智能体 → 固定构建/浏览器/页面检查 → 审查智能体 → 交付或交回开发修复 → 重建与再次审查。最多三轮修复，达到任一限制即停止并保留已有产物。三个角色顺序运行，保持单运行槽与本机内存保护。

每个角色有独立提示、允许的工具集合、自己的有界决策循环和结构化输出。规划最多6步，审查每轮最多8步；不是把已有阶段换名称，也不是只调用三次模型。开发沿用持久化任务执行器。审查上下文只包含冻结规格、当前文件索引、自己的工具结果及技术证据，不包含开发模型的私有推理。交接传递计划、源码摘要、审查报告等明确产物。

初次产品方案仍需用户确认，不因多智能体而省略。全栈仍限确认的CRUD schema与固定后端，仍只允许最多12页/128文件/固定依赖。

## 权限、预算与恢复

- 后端以ToolContext.agent_id强制检查权限，模型输出不能自行切换角色。回执指纹含角色；不能借另一个角色的回执越权。
- 三角色共用已选文字模型、run_id、费用台账、任务调用数上限与开发步骤上限（默认40）。前期方案费用仍计入同任务费用，但不占确认后的开发决策步数。多角色可能增加Token使用，不能预先保证更便宜或效果更好。
- 请求/结果存在tools.sqlite3的agent_calls，交接/审查/当前角色进入SQLite checkpoint及运行记录。备份会保留新表。既有tools.sqlite3只新增表，不重写旧数据。
- 已保存结果重复恢复不再次调用模型、不重复记步数；模型层已存回执但角色保存中断时恢复已有回执。无法确认上次请求结果时停止，保留费用预留，不悄悄重试；发送前的配置/预算拒绝允许修正后恢复。无自动备用模型。
- 审查结果绑定源码、冻结需求、固定运行环境、测试套件与审查策略。无完整逐条标准、引用未读取文件或当前技术未通过时，禁止提交ready_for_manual。交付前再次核对依据；读取历史审查发现依据变化时标为失效。
- supported表示模型判断有已读取源码证据，**不表示自动证明需求通过**。manual表示需要人工核对。人工验收记录仍由用户操作，任何智能体都不能代填。

## 使用与交付

无需新增Key或开关。重启新版工作台后，新确认开发的任务使用三个角色。运行详情显示角色状态、共享步骤、逐条审查、交接记录；Trace标记角色，费用明细区分规划与审查。源码ZIP新增AGENT_TEAM.json，交付报告包含交接及逐条审查。导出是当时快照。

旧任务未带orchestration_version，按原图节点继续恢复，不自动转成新任务。源码恢复仍创建暂停的验证副本，不因此启动智能体或消耗API。已登记0.2.0、0.3.0–0.3.3可并排升级到0.4.0；降级仍需旧目录与原数据，不将新数据写回旧版。

## 0.4.1 协作收尾（2026-11-09）

1. **停止与导出**：限额、主动停止、环境不可用时明确终止审查状态。环境摘要允许标记不可用，交付不依赖Docker在线；源码安全校验仍必须通过。异常退出尽力导出已有源码、Trace和失败报告，不能安全导出时保留原文件并说明原因。环境证据缺失不显示为当前验证通过。源文件、磁盘或Git本身损坏时不承诺强行导出。
2. **审查预留**：新任务开发阶段在原总限额内保留3步、3次模型调用空间；估算费用保留任务预算的20%或所选模型3次最低预留额中的较大者，最多为任务原上限。默认5元任务保留1元估算空间。开发将触及预留时先停止，再构建当前源码并交给审查；未完成开发不能被审查标为整体完成。预留不是新增消费，也不能保证一定足够三次实际请求（上下文长度影响预留），仍受原全局/任务预算保护。费用台账不重置。旧任务没有team_policy_version，不追加这些资源限制。
3. **规划覆盖**：每条冻结标准须由开发任务关联，或显式指定固定构建/页面检查、人工核对及理由。检查漏项、重复责任和非法序号；责任分配不等于需求覆盖证明或验收通过。采用新的版本化输出Schema，旧任务仍使用原Schema。
4. **问题复查**：按验收序号生成稳定问题编号，保留每轮源码摘要、实际改动文件、审查引用位置、技术证据和结论。开发和下一轮审查获得问题清单；已有问题只有当前读取证据支持才能关闭，改成“人工核对”不能消除缺口。源码、运行环境及技术结果均未变化时，在下一次模型审查前停止；同一标准连续三轮未解决时提前停止。默认最多三轮修复的总限制不变。人工记录仍独立。
5. **离线检查**：增加审查资源预留、规划责任分配、旧问题不能被抹掉、无变化提前停止、Docker不可用仍安全导出等回归。第八组team_scenarios覆盖三页面、既有项目增量维护、全栈CRUD、无有效修复及额度交接；所有模型响应固定在本地，实际构建/浏览器检查仅在受控容器运行。

界面新增责任分配、预留规则与问题复查记录；源码ZIP的AGENT_TEAM.json包含plan_coverage、review_issues、review_history和停止原因。历史文档中的七组验证是0.4.0记录，当前离线流程为八组。真实模型、Windows完整运行和正式Release继续暂缓。

本轮本地验证：241项Python回归、10项前端专项检查、类型/格式/构建及八组离线流程通过；新增第八组包含上述五个协作场景。最终证据保存在本机outputs/team-closeout-offline与outputs/team-closeout-summary.json。所有响应为固定合成数据，真实模型/视觉/Dify调用为零；这不证明真实模型自主完成率，也不代表Windows完整运行验收。
